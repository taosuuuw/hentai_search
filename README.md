纯前端（HTML/CSS/JS，零依赖、零构建）的成人向同人志**元数据聚合搜索界面**，外加一个**零依赖的本地网关**
（`tools/gateway.js`，只用 Node 内置模块）用来打通需要签名 / 需要绕开跨域的站点；
**2.0 起支持在站内直接在线阅读**（`assets/js/reader.js` + 网关 `/api/reader`），不用再跳到原站看图。

## 快速开始

```bash
node tools/gateway.js
# 然后用浏览器打开 http://127.0.0.1:8788/
```

网关同时充当静态服务器，所以页面与接口**同源**，连跨域都省了。启动后页面会在 1 秒内自动识别到它。

**网关会自动沿用你系统里的本地代理**（Clash / v2ray 之类，通常监听 `127.0.0.1:7897`）：
Chrome 走它、Node 默认不走，所以网关启动时会探测常见端口并用 `CONNECT` 验一次，命中就带着
`HTTPS_PROXY` 重启自己（Node 只在启动时读取代理配置）。

**但出口不再粘死**（3.0 起）：启动时探测到的代理只是「原路」，运行期还会重判 ——
代理中途挂了会自动改走直连（`DoH 钉真 IP` / `境内中继`），之后代理又起来也会被认出来，
两种情况都**不需要重启网关**。所以「必须挂全局代理才用得起来」不再成立：禁漫 / 拷贝漫画 / 绅士漫畫 /
nhentai / E-Hentai / hitomi 在**不挂任何代理**的情况下都有实测可用的通路（细节见下方「出口三层」）。

```bash
node tools/gateway.js --port 9000
node tools/gateway.js --proxy http://127.0.0.1:7897      # 手动指定出口代理
node tools/gateway.js --no-proxy                         # 强制直连
```

**或者直接双击项目根目录的 `start-engine.cmd`**（2.0 新增，省去手敲命令）：

```bat
start-engine.cmd                    :: 停掉旧引擎 → 起新引擎 → 等就绪 → 自检 /api/reader → 打开浏览器
start-engine.cmd -Status            :: 只看状态（在不在跑、是不是新版本）
start-engine.cmd -Stop              :: 只停引擎，不启动
start-engine.cmd -Port 8899         :: 换端口
start-engine.cmd -NoBrowser         :: 启动后不自动开浏览器
start-engine.cmd -Foreground        :: 不新开窗口，日志留在当前窗口（Ctrl+C 停止）
start-engine.cmd -KeepOpen          :: 引擎就绪后不自动关掉启动器窗口
```

启动器只终结**占用该端口的 node 进程**（其它进程一律不碰），随后用当前代码起新引擎，并真的打一遍接口自检：
`/api/ping` 判断是不是新版本、`/api/reader` 能不能取到 nhentai 与 MangaDex 的页。
引擎正常时启动器 3 秒后自动关闭并留下引擎窗口；出错时窗口会停住，方便你把报错复制出来。

> 启动脚本以 **ASCII-only** 编写是刻意的：cmd.exe 解码非 ASCII 字节时可能在解析阶段就崩掉，
> 于是窗口一闪而过（`pause` 都来不及执行）——旧版启动器正是栽在这里。
> 另外 `tools/start-gateway.ps1` 的头部注释里提到的 `start-gateway.cmd` 是过时名字，实际入口是 `start-engine.cmd`。

### 启动方式（Windows / macOS / Linux）

三个入口做的事完全一样：停掉占用端口的旧 node 引擎 → 用当前代码起新引擎 → 轮询 `/api/ping` 等就绪 →
自检 `sources` 里有没有 `pixiv`、`/api/reader` 能不能取到 nhentai / MangaDex 的页 → 打开浏览器。

| 系统 | 入口 | 说明 |
| --- | --- | --- |
| Windows | 双击 `start-engine.cmd` | 转调 `tools/start-gateway.ps1`，参数写成 `-Port 8899` / `-Stop` / `-Status` |
| macOS | 双击 `start-engine.command`，或终端里 `./start-engine.sh` | `.command` 只是转调 `start-engine.sh` 的极短包装（给双击用） |
| Linux | `./start-engine.sh` | 没有 cmd / PowerShell，直接跑 bash 版 |

macOS / Linux 首次使用先给一次可执行位：

```bash
chmod +x start-engine.sh start-engine.command
```

```bash
./start-engine.sh                    # 停旧引擎 → 起新引擎 → 等就绪 → 自检 /api/reader → 开浏览器
./start-engine.sh --status           # 只看状态（只读，不动任何进程）
./start-engine.sh --stop             # 只停引擎，不启动
./start-engine.sh --port 8899        # 换端口（默认 8788）
./start-engine.sh --no-browser       # 启动后不自动开浏览器
./start-engine.sh --foreground       # 不后台运行，引擎日志留在当前终端（Ctrl+C 停止）
./start-engine.sh --keep-open        # 引擎就绪后保留输出（对齐 Windows 的 -KeepOpen）
./start-engine.sh -- --proxy http://127.0.0.1:7897   # `--` 之后的参数原样转给 tools/gateway.js
```

macOS / Linux 版**默认后台运行**（`nohup` + `disown`），引擎日志写在 `tools/gateway.log`；
起不来时启动器会把该日志的尾部直接打出来。退出码与 Windows 版完全一致：
`0` = 引擎已就绪、启动器可退出；`2` = 正常收尾但要保留输出（`--status` / `--stop` / `--keep-open`）；`1` = 失败。

> 它只终结**进程名是 `node`** 的占端口进程；换成别的进程占用时只打印警告并退出，绝不动别人的进程
> （macOS 用 `lsof` 找占用者，Linux 优先 `ss -lptn`、没有再退 `lsof`）。
> 自检的 JSON 解析走 `node -e`，不依赖 `jq`；只有在 `curl` 也缺失时才改用 `node` 直接发请求。

> 旧的 `--picacg-email / --picacg-password` 参数在网关里还在（`/api/picacg/*` 没删），
> 但**前端已经移除了哔咔信息源**，所以现在传了也没有入口会用到。

不想用网关也可以（`python -m http.server 8777`，或直接双击 `index.html`），
但禁漫会退化为镜像 HTML 检索，且拷贝漫画 / Kemono / Pixiv 不可用。

## 为什么需要那个本地网关

禁漫天堂、拷贝漫画、Kemono 的接口都有共同点：**必须带自定义请求头**（`token` / `signature` / `Host` / …），
**响应还常常是 AES 加密的**，而且**都不返回 `Access-Control-Allow-Origin`**。浏览器三样都做不到：

- 自定义请求头会触发 CORS 预检，而公共 CORS 代理不转发请求头；
- 浏览器里没有 MD5（JM 的 token 与 AES 密钥都基于 `md5(时间戳+密钥)`），也没有 ECB 模式的 AES。

调研了两个现役实现（`ComicSparks/jasmine`、`venera-app/venera`）后发现：它们能直连**不是因为找到了什么巧办法**，
而是因为**都是原生客户端** —— jasmine 的 HTTP 全部在 Rust 层用 FFI 发出（Dart 层连 `dio`/`http` 都没装），
venera 走 `dio` + `rhttp` 原生 socket，原生环境压根没有同源策略。两者都没有用任何第三方聚合 API。

所以本项目把「原生层」换成一个**本机 Node 进程**：签名、解密、取页面、统一 UA/Referer 都在网关里完成。

| 网关接口 | 做的事 |
| --- | --- |
| `/api/jm/search` | 禁漫：启动拉**实时域名列表**（base64 + AES-256-ECB，密钥 `md5("diosfjckwpqpdfjkvnqQjsik")`，来自 `venera-configs/jm.js`）→ 请求带 `token = md5(时间戳+"18comicAPPContent")` / `tokenparam` / `X-Requested-With` → 响应按 `md5(时间戳+"185Hcomic3PAPP7R")` 的 AES-256-ECB 解密 → `/setting` 下发图片 CDN |
| `/api/copymanga/search` | 拷贝漫画：从 `api.copy-manga.com/api/v3/system/network2` 动态发现节点 + `x-auth-timestamp`/`x-auth-signature` HMAC 签名；节点失败自动换下一个 |
| `/api/kemono/search` | Kemono：`kemono.cr/api/v1/posts?q=&o=`（每页 50 条），封面 `data{file.path}`，详情 `/{service}/user/{user}/post/{id}` |
| `/api/porncomic/search` | porn-comic：HTML 站，`/q/{词}-{页}.html` + `/tags/{词}.html` 兜底，解析 `a.thumb`。**通路顺序 3.2.0 起 = ① 直连 → ② 本机 Chrome 过 Cloudflare → ③ 境内中继**（旧顺序把中继排在 Chrome 前，实测中继现在整条链超时、Chrome 每次 6–9 秒出数，等于每次检索先白等十几秒）。带**通路记忆**（10 分钟）、**单次取页总预算 20 秒**、中继**人均一份剩余预算**（旧版每个中继各吃满 20 秒 ⇒ 冷启动一次就耗掉 16–18 秒）。空结果只认**站点自述**：标题里出现 `no result` 才回「0 条」，其余情况继续试下一个入口 |
| `/api/lectormanga/search` | LectorManga：`lector-mangas.lat/comics?search={词}&page={页}`（**不是 `?q=`**），切 `#directory-results` 段解 `.card-cover-link`。三个域名轮换（`lector-mangas.lat` / `lectormangass.com` / `lectormangaa.com`）。「真页面 + 0 条」如实回 0 条，不编成故障 |
| `/api/porncomic/solve` | 自检：本机 Chrome 到底能不能过 Cloudflare（`?tag=` 或 `?url=` 指定页面，`?force=1` 无视冷却强制重试） |
| `/api/picacg/search` | 哔咔（**前端已移除这个源，接口仅保留**）：`HMAC-SHA256(key, lowercase(path+time+nonce+METHOD+apiKey))` 全套头 + `POST /comics/advanced-search`，`authorization` 由 `/auth/sign-in` 代登录取得 |
| `/api/proxy` | 通用中转（自动补 Referer/UA），给 wnacg / Hitomi / 自定义源这类 HTML 源用；三层都打不通的域名进冷却（限流 45s / 真不可达 3 分钟），成功的响应进进程内缓存（5 分钟 / 64MB 上限）；**自动跟随 301/302**（绅士的 `www.wnacg.date → www.wnacg.com`、porn-comic 的检索页 302 都靠它） |
| `/api/wnacg/search` | 紳士漫畫检索（3.2.0 新增）：**分批竞速**镜像（每批 3 个，先到先得）、跟随镜像重定向、记住最近成功的镜像 + 失败主机冷却、结果缓存 5 分钟。前端拿它当第一优先，取不到才退回浏览器那套 HTML 竞速 |
| `/api/diag` | 出口自检：网关现在到底能打到哪些站，**并注明每一站是靠哪一层打通的**（`via: env / doh / relay`），页面用它修正「站点不可达」的误判 |

### 出口三层：为什么**不挂全局代理也能用**（3.0 新增）

不挂任何代理时的实测（`node tools/netprobe.js`，完整数据见 `docs/research/sources-probe.md` 第 5 节）
把「打不开」拆成了四种完全不同的死法，并据此做了三层补偿：

| 层 | 做什么 | 治的是哪种死法 |
| --- | --- | --- |
| ① 原路 | 全局 `fetch`（启动时探测到的本地代理由 undici 自动带） | **本机配了本地代理时走的就是这一层，行为与改造前逐字一致** |
| ② 直连强化 | DoH 多解析器并取候选 → 带 SNI + **证书校验**逐个验真 → 钉住可用 IP 直连 | DNS 污染（紳士漫畫 / hitomi：同一个域名，阿里 DNS 给假 IP、腾讯 DoH 给真 IP） |
| ③ 中继 | 境内直连可达的 Cloudflare 中继（AllOrigins 取文字/JSON/图片、i0.wp.com 取图片） | SNI 阻断 / 整段不可达（nhentai、E-Hentai、danbooru、i.pximg.net） |

三件事必须一起做才有意义：

1. **出口不再粘死**。旧实现一旦在启动时探测到本地代理就把 `HTTPS_PROXY` 写死，代理一关，
   每个请求都先撞那个没人监听的端口（日志里是 `ms=5 的 fetch failed`）——
   **连本来直连就通的禁漫 APP 接口 / 拷贝漫画 API 也一起被废**，这才是「代理一关就全废」的头号原因。
   现在出口是**运行期**判定的：没有可用代理时每 10 秒重探一次，有代理时 60 秒一次，
   任何请求失败立刻重探；代理中途挂掉自动改走直连，之后代理又起来也会被认出来（都不需要重启）。
2. **验真口径必须和真实请求一致**。反例：墙外 DNS 把 `api.copy-manga.com` 解析到
   `api.copy2000.online` 的 IP 上，宽松验真会钉住这个 IP，之后每次真实请求都必然 TLS 失败。
3. **`http://` 取不到要再试 `https://`**。绅士漫画的正文图给的是 `http://img5.qy0.ru/...?verify=…`，
   同一个地址 `http` 被重置（`ECONNRESET`）、`https` 返回 `200 image/jpeg 150802B`。

> <summary>📌 批注：出口三层 · 代价与边界（3 条）</summary>
>
> 【已实测】三层在不挂任何代理时的端到端结果：禁漫（检索 80 条 / 阅读 275 页 / 封面）、拷贝漫画（10 条 / 24 页 / 封面）、紳士漫畫（前端 9 条 / 阅读 90 页 / 封面）、nhentai（25 条 / 16 页 / 封面）、E-Hentai（25 条）全部可用；界面检索 35 条结果、成功源 5/7，首次 36.8s、同会话第二次 10.7s。

## 界面结构

整个页面**只有一个搜索框**，其余设置都收在它**上方的抽屉**里：

```
┌─────────────────────────────────────┐
│  hentai搜索                          │  紧凑标题（面板拉出时自动淡出让位）
│  ┌─── 筛选面板（从搜索框顶部向上拉出）───┐ │
│  │  作品类型 / 语言 / R18G / AI / 画师 … │ │
│  └──────────────────────────────────┘ │
│  ────────  ≡  ────────               │  ← 垂直滑块（按住向上拉）
│  向上拉出筛选                         │  ← 拉手条（贴在搜索框上沿）
│  [ 🔍 搜索标题、社团、画师、标签… ] [搜索] │  ← 唯一输入
├─────────────────────────────────────┤
│  网络提醒（仅在探测到受限时出现）      │
│  检索思维链（仅检索时出现，紧贴搜索框，折叠成一行）│
│  结果卡片（紧跟其下，单页铺开，滚到底继续加载）│
└─────────────────────────────────────┘
```

- **抽屉从搜索框顶部向上展开**：滑块与拉手条贴在搜索框**上沿**，按住**向上拉**面板就从顶部往上升，
  同时搜索框本身向下让位（最多 17vh），顶边会一直升到距视口顶部约 10px。拖到一半松手停在那儿，两端自动吸附。
- **面板不再压住标题**：搜索区上方固定留 52px 让位（拉手条约 32px，余量不会被吃掉）；
  面板拉出时「hentai搜索」标题与说明自动淡出并上移，收起后立刻回来。
- **思维链贴着搜索框底部**：总高约 60px，折叠态只显示**一行清晰的当前步骤**，更早的行以 `blur(2.6px)` 模糊退场；
  展开后全部清晰可读。
- **联想泡泡会主动给思维链让位**（3.2.0 修）：泡泡层默认贴着搜索栏下沿，而那里正是思维链的位置 ——
  之前输入时泡泡会整片压住思维链。现在只要思维链的底边还在泡泡默认位置之下，泡泡就整体让到它下面，
  并用 `ResizeObserver` 跟着思维链长高（思维链在检索时会逐源加行）；思维链不可见时清掉内联样式、
  完全回到 CSS 默认，所以「还没检索过」的观感一个字没变。
  （实测几何：搜索条容器底边 y=419、思维链 y=435→505、泡泡默认 y≈429 → 改成 y=512.95，不再重叠）

## 功能

### 1｜内容分级换成 R18G / AI 筛选

原来的分级控件整体移除；新增 **猎奇 / R18G** 与 **AI 绘画** 两个三段式开关（`不限 / 只看 / 排除`）。
源站支持就在服务端拼标签，所有源返回的条目还会按内置词表本地兜底打标后再过滤。

### 2｜汉化 / 中文特别标出，并在相似结果里排前面

- **识别**：标题/标签/语言里的 `汉化`、`漢化`、`汉化组`、`个人汉化`、`中国翻译`、`[Chinese]`、`[中文]`、
  `中文版`、`官中`、`z h`、`language: chinese` 等（`NS.ZH_SCAN` / `ZH_LANG`）。区分 `汉化`（有翻译）与 `中文`（标明中文）。
- **标出**：卡片左上角绿色角标 `汉化` / `中文`，排在源名角标**之前**，最显眼的位置。
- **排序**：相关度分数里加 `+4.5`（明确汉化再 `+1.5`）；并且对「相似结果」做一次再归组
  （按去掉括号标记的宽松标题指纹），**组内有中文的排到该组最前面**，组的整体位置不变，不会打乱相关度。
- **去重不丢信息**：跨源同一作品合并时，任一变体有中文，这一条就算有中文。
- **筛选**：结果工具条上有 `汉化/中文 N` 胶囊，可一键只看中文；结果统计里也会报「N 个有汉化/中文」。

### 3｜结果量动态分配 + 单页向下滚动加载

- **动态分配**（默认）：目标总数 ÷ 启用源数，下限 6、上限 60。
  只开 1–2 个源时会额外多要（`+6`），所以「源少也能一次凑几十条」；
  6 个源时每源 10 条 ≈ 60 条；也可以切成「固定每源条数」。
  抽屉里那一栏在自动模式下就是**目标结果总数**（默认 60，可调到 200），旁边实时显示分配算式。
- **只有一面**：结果不再分页。先铺一批（`pageSize`，默认 60，可在设置 → 搜索里改），
  底部哨兵进入视野（提前 700px）就自动追加，**没有上一页 / 下一页，也没有划动手势**。
- **两级加载**：本地候选池还有没铺开的 → 直接铺、不发请求；本地铺完了但没到底 → 才向各源再要一批
  （沿用同一套时间上限），回来接着铺。底部会写明当前状态（已显示 N / M 张 · 正在索取 · 已经到底）。
- 候选池始终按相关度全局排序，追加不会改变已有排序。

### 4｜检索策略按查询意图分流

输入框里的词会先被判类，再决定「按标题查」还是「按标签查」：

| 意图 | 判定依据 | 采用的策略 |
| --- | --- | --- |
| 作品名 `title` | 带 `[社团]` / 引号，或词数 ≥4 | **尽量完全对上名字**：MangaDex 走 `title=`，本地重排里完全同名 `+16`、前缀 `+7`、包含 `+3`，命中打「精确」角标 |
| IP / 角色 `character` | 命中系列词典（fate / blue archive / hololive…），或 1–2 个短词 | **尽量命中对应标签**：MangaDex `includedTags[]`、nhentai `tag:"…"`、E-Hentai `"…"$`、Danbooru 标签；网关类源改用规范系列名 |
| 体裁 / 题材 `genre` | 命中约 25 组题材词表（全彩 / NTR / 百合 / 巨乳 / 拘束…） | **尽量罗列相关题材**：多标签 `OR` 扩召回（MangaDex `includedTagsMode=OR`），本地重排按命中题材词数加权（每词 `+5`，上限 `+14`） |

判定优先级：括号或长词 → 系列词典 → 题材词表 → 短词当角色名 → 其余按作品名。
结果统计里会直接写出这次用了哪种策略（例如 `策略 IP / 角色（fate）`），思维链第一步也会说明。

### 6｜作品类型 + 卡片标签 + 同系列堆叠

**作品类型**：同人志 / 短漫 / 长篇连载 / 插画集 / CG 集 / 合集-选集 / 商业单行本 / 韩漫 / 欧美 / Cosplay / 3D。
源站有原生分类就用原生，没有就按标题/标签/页数本地推断。

**卡片标签**：每张卡片正文下方列出最多 6 个标签（超出显示 `+N`，一个都没有则显示「无标签」）。
`R18G` 与 `AI` 双重标注：封面左上角有专用角标（红 / 青紫渐变），标签里对应的词也单独高亮，
和筛选面板里的 R18G / AI 开关共用同一套词表。

**同系列堆叠**（约 100 条系列词典，长词优先）——**只叠「确实同系列」的**：

- 先要命中系列词典，**再要至少满足一条高度相符**：
  ① 同名（宽松标题指纹一致，含语言 / 汉化变体）② 同画师（画师串相同或互相包含）
  ③ 名字高度相似（一个标题完整包含另一个）。
  既不同画师、名字也对不上的，一律单张平铺，不参与堆叠。
  **不用「共同标签数」当判据**：`Doujinshi` / `Oneshot` / `Loli` 这类通用标签任何两本同系列作品都共有，
  等于没筛（实测会把 14 本画师各异的 Fate/Grand Order 同人志叠成一摞）。
- 静止时多张卡片带 4.5px 位移与 1.15° 旋转叠放，角标显示「N 本同系列」。
- **悬停整摞像手牌展开**：每张按索引位移 `56px`、抬升 `10px`、旋转 `3.4°`；整摞 `z-index` 提到 80，
  **扇出的卡片会盖住左右两侧的作品**；靠右边缘自动改为向左展开。
- **鼠标停在哪一张，哪一张就过渡到最顶层**：抬起 `9px` + 放大 `1.05` + 加重阴影 + 强调色描边。
  这里不用逐张卡片的 `:hover`（重叠时命中会在卡片之间跳），而是用**未抬起的几何位置把指针 x 映射到卡片索引**
  （扇开后每张只比上一张多露一个 `step`，所以从左到右依次对应第 0、1、2… 张）——
  移动是单调的、切换自然，被抬起的那张变大也不会抢走指针。
- 触屏点一下摊开；点「展开全部 N」切到该系列的单列视图；
  超过平铺上限（5 张）的会补在堆叠后面单张展示，一张都不会丢。

### 7｜初始模糊（封面 + 角标 + 标签，所有作品一视同仁）

- **开关**：设置 → 外观 → 「检索结果初始模糊」。**打开就是所有作品一律糊** —— 封面、封面上的角标、卡片底部的标签行一起糊，
  悬停或点「点击显示」才露出。
- **R18G / AI 不参与模糊逻辑**，它们是**筛选条件**：筛选面板里有「猎奇 / R18G」与「AI 绘画」两个三段式开关（`不限 / 只看 / 排除`），
  要排除这类作品就在那里排除。
- 实现上只有 `html.hs-blurcovers` 一个状态类，模糊规则全部限定在 `.hs-card` 内部（放大视图另有一套）。
- **成人向筛选**（筛选面板 → 「成人向」，**只有两档、没有「不限」** —— 这是专门搜本子的引擎）：
  「滤掉非成人向」（默认）/「只留已确认」，鼠标悬停在按钮上会给出这一档的解释。
  判定优先级：① 源自己的分级字段最可靠（MangaDex `contentRating`、Danbooru `rating`、Pixiv `xRestrict`）
  → ② 源本身就是成人站（`HS.ADULT_SOURCES`：禁漫 / 紳士漫畫 / E-Hentai / nhentai / Hitomi / porn-comic）
  → ③ 标签或标题里出现成人词（`HS.ADULT_TAGS`）。
  三者都不命中就是「未知」，**未知不硬杀**：跨源去重时，同一本只要在别的源被确认过成人向，合并后就算成人向
  —— 这就是「比较模糊时由其他途径检验」那一层。想更狠就切「只留已确认」（未知也剔除）。

### 10｜凭据怎么放（Pixiv）

- **Pixiv**：R-18 需要你自己登录后的 `PHPSESSID`（设置 → 搜索 → Pixiv），这个 cookie 存在本机 localStorage，清浏览器数据即消失。不填时 pixiv 会把 `mode=r18` 静默回落成全年龄，所以网关按数据本身（`xRestrict` / `R-18` 标签）打标，**不会把全年龄条目误标成 R-18**。
- **哔咔已移除**：这个源连同设置里的账号密码入口一起去掉了（官方 API 需要 HMAC 签名 + 登录 token，收益不值这个维护成本）。网关里的 `/api/picacg/*` 接口保留着，但前端没有任何地方会调用它。

### 13｜再次提交搜索 = 当场打断上一次检索（3.2.0 新增）

以前检索中再按回车等于**什么都没发生**（`if (searching) return;`）——
用户只能干等最慢的源把 22 秒预算耗完。现在新的一次会**当场接管**，分两层：

1. **网络层**：每次检索开一个 `AbortController` 作用域，本次检索发出的每个请求都挂在它上面
   （多源 × 多候选串 × 代理链重试）。下一次提交搜索时 `HS.net.closeScope()` 一次性 abort，
   那一批在途请求在**同一帧内**全部断开 —— 不是等它们超时。
2. **逻辑层**：检索代次 +1，旧链路里每一处 `await` 之后（打字机、网络探测、信息源选择、
   并行检索、聚合、重排）以及每个回调（逐源进度、流式 push、`finally` 里的状态复位）
   第一件事就是比对代次，不是最新一代就**就地退出、一个字都不写**。

两层缺一不可：只 abort 网络的话，旧链路 catch 到 `AbortError` 仍会去写 DOM；
只比代次的话，旧请求会继续占着连接和并发额度。实测踩到的两个具体症状都已修掉：

- 被打断的旧检索会把「探测网络环境 / 选择信息源 / 并行发起检索请求」这些行
  **追加到新检索的思维链上**（同一条「启用：…」重复出现两次，像是新检索自己发了两遍）；
- 旧检索的 `finally` 会把新检索的「检索中」按钮和 `HS.busy` 一起清掉
  —— 界面显示可以再点，实际还在跑。

作用域是精确的：探测 / 网关卡体检 / 封面图这些自己不带 scope 的请求**不受影响**，
不存在「关一个把全站请求都掐了」的副作用。

> 顺带修掉的相邻问题：**联想泡泡与思维链重叠**。泡泡层是绝对定位在搜索条下沿的，
> 而正下方就是思维链面板，所以打字时整片压住它。3.2.0 改成**把思维链往下顶**
> （`#chain-panel` 的 `--hs-chain-gap`，由 `suggest.js` 按实测几何写入），
> 在「搜索框」与「思维链」之间腾出恰好容纳泡泡的一段 —— 最终顺序是
> **搜索框 → 联想泡泡 → 思维链 → 结果**，两边都不遮。
> 早先的做法是「把泡泡让到思维链**下面**」，那会把泡泡推进结果区、挡住结果文字。

## 性能说明

- 遮蔽走「预置遮罩 + 零过渡」路径：按键 → 写 class → 下一帧即可见。
- 检索全并行、**先返回的源先出结果**（流式渲染）；每源独立时间预算（直连 13s / 需代理 16s），
  另有 **22s 全局上限**：到点把没回来的源标成「超时已跳过」。
- 6 个源实测并行 6.4–14.9s 全部返回；网关侧对同名域名做 45s 失效冷却，避免反复空跑。
- 公共代理整条链失败后 60s 冷却；网关在线时优先走网关（同源、带正确 Referer/UA），
  并且**不再叠加公共 CORS 代理链** —— 网关自己就有「DoH 钉真 IP / 境内中继」，两边同时打同一批
  中继只会抢同一个限流配额（实测把 AllOrigins 打成 429 之后两侧同时全灭）。
- 网关侧：每台主机会记住「哪一层有效」（`hostPlan`，10 分钟），所以只有会话内第一次付 DoH / 中继的探测成本；
  同会话第二次检索实测从 36.8s 降到 10.7s。中继响应进进程内缓存（5 分钟 / 64MB 上限），
  真被墙的镜像进冷却（限流 45s、真不可达 3 分钟），避免反复烧掉限流配额。
- 面板用 `max-height` + `padding-top` 过渡，拖动期间关闭过渡跟手；结果首屏只渲染 `pageSize` 张，
  其余由底部哨兵（`IntersectionObserver`，提前 700px）按批追加，DOM 不会一次性撑爆。
- 动画强度可调「精简 / 关闭」，并自动尊重 `prefers-reduced-motion`。

## 已知限制

- **禁漫的图片反混淆未实现**（JM 对部分章节做了行重排）——本项目只做元数据检索，不下载图片，不影响搜索。
- **porn-comic 依赖本机 Chrome 过 Cloudflare**：站点全站前置人机验证，网关自己不会执行 JS，所以用零依赖 CDP（`--headless=new` + 真身 UA + 反自动化补丁）驱动本机已装的 Chrome/Edge 取页面。需要 Node 22+（自带全局 `WebSocket`）。没装 Chrome 可用 `HS_CHROME` 指路；被卡时可试 `HS_CF_HEADFUL=1`（有头模式），或干脆换一个出口 IP —— 数据中心 IP 的 Cloudflare 名声很差，这是最容易踩的坑。
- **哔咔已移除**：源、登录入口、网关设置项全部删掉了；网关里的 `/api/picacg/*` 接口仍在（零依赖、本机端口），但前端已无调用点。
- 紳士漫畫 / E-Hentai / Hitomi 是 HTML 解析，站点改版会失效（都写了容错与兜底选择器）。
- 本机 DNS 屏蔽了不少域名，所以「能不能用」取决于网关能不能打通它 —— 但**不取决于你有没有挂全局代理**：
  网关有三层（原路代理 → DoH 钉真 IP → 境内中继），不挂代理时多数站也能用，且每站会注明靠哪一层打通的；
  抽屉 → 本地网关 → **「检测」会跑一次出口自检**（`/api/diag`），明确告诉你现在哪些站能打通、分别走哪条路。
  **升级到本版后必须重启一次网关进程**：出口不再粘死的逻辑在新进程里才生效（`start-engine.cmd` 会自己停旧起新）。
- **E-Hentai 的「搜不到」有两个不同的真因，别混为一谈**（3.2.0 起网关会把它们分开讲）：
  ① **搜索侧按出口 IP 限制** —— 机房 / 数据中心 IP 常拿不到搜索页（换住宅节点可解）；
  ② **限流软封锁** —— 上游会回「**HTTP 200 + content-length: 0**」的空壳（响应头里 `via: 1.1 varnish`），
  同一出口连续请求就会触发，**和请求头、cookie 都无关**（对照实验见 `docs/research/sources-probe.md` 第 6.1 节）。
  旧版本把空壳当成「成功返回的空结果」，于是页面显示「搜索接口在当前出口返回空集」—— 一个听起来很确定、其实是误判的结论。
  现在：空壳一律判失败 → 自动改走中继（另一个出口 IP）→ 还不够才退到 `/torrents.php?search=` 兜底；
  识别到空壳后该主机进 60 秒空壳冷却，冷却期内不再硬撞（越撞封锁越久）。等 1–2 分钟再搜通常就恢复了。
- E-Hentai 搜索结果缓存 4 分钟、阅读器逐页限速 300ms；Danbooru 匿名最多 2 个标签（适配器自动截断）。
- **porn-comic 现在有三条通路**：直连 → **本机 Chrome 过 Cloudflare** → 境内中继。
  3.2.0 起把中继挪到最后：实测公共 CORS 代理（allorigins / allorigins-get）现在整条链超时，
  而本机 Chrome 每次 6–9 秒就能出数 —— 旧顺序等于每次检索先白等 16–20 秒，这正是
  「porn-comic 经常超时无返回」的主因（前端聚合器只给每个源 22 秒）。
  另加：通路记忆（10 分钟）、单次取页总预算 20 秒、中继人均一份剩余预算、
  挑战页 4.5 秒判死（不再空转到超时）。实测：命中 6–7 秒、二次命中走缓存 2ms、
  无结果从「60 秒超时 502」变成「18 秒 200 + 0 条（站点自述 no result）」。
- **紳士漫畫优先走网关的 `/api/wnacg/search`**（分批竞速 + 跟随镜像重定向 + 镜像记忆 + 结果缓存 5 分钟）；
  网关不在时才退回浏览器那套 10 镜像全量竞速。镜像池里有几个（`www.wnacg01/02/03/05.cc`、`www.wn07.ru`）
  是真的被 SNI 阻断，会被迅速跳过并冷却 —— 这是**镜像本身的死**，不是引擎的问题。
- 同系列归并依赖内置词典（约 100 个常见系列），并且要求「同名 / 同画师 / ≥2 个共同标签」至少满足一条；
  词典外的作品作为独立卡片展示。
- 汉化判定基于标题/标签文本，可能有个别误判（例如标题里带「中文」但其实是原文）；角标只作提示。
- 追加加载依赖各源的分页参数，个别源（Hitomi / 自定义源）没有分页，追加时会重复第一批并被去重，
  这时会较早判定为「已经到底」。
- **在线阅读依赖网关联网取页**：阅读器本身不直连图床，页地址全部由 `/api/reader` 与 `/api/proxy` 提供；
  网关没起来就会「能搜不能读」。但**不要求挂任何代理**：nhentai / E-Hentai / 紳士漫畫 / Hitomi
  这些站在不挂代理时由网关的 DoH 钉真 IP（紳士 / hitomi）或境内中继（nhentai / E-Hentai）打通 ——
  实测已读到图（见上方「出口三层」与 `docs/research/sources-probe.md` 第 5 节）。
